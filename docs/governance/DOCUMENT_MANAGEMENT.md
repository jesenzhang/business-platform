# 项目文档管理规范

> 文档 ID：DOC-GOV-001  
> 版本：1.0  
> 状态：Baseline  
> 生效日期：2026-07-30

## 1. 目的

建立单一、可追踪、可归档的项目文档体系，避免以下问题：

- 架构、实现和计划分别存在多份互相冲突的说明；
- 文档散落在仓库根目录、聊天记录或临时目录；
- 旧设计被静默覆盖，无法判断当前权威版本；
- 执行计划长期留在当前目录，完成状态不清；
- 代码变化后文档长期失真；
- 编码 Agent 无法确定应遵循哪份规则。

## 2. 管理原则

### 2.1 单一权威来源

每个主题只能有一份当前权威文档。补充文档必须引用权威文档，不得复制并独立演进同一规则。

### 2.2 文档即版本化资产

文档与代码共同进入 Git，使用相同评审、提交和追溯机制。聊天记录、Issue 评论和外部笔记不能作为长期权威来源。

### 2.3 现状不自动成为规范

代码现状可能是过渡实现或缺陷。权威文档与实现冲突时，应先判断文档是否仍有效，再决定修代码或通过 ADR 修改基线。

### 2.4 不静默覆盖历史

被替代的架构、ADR、计划和评审必须保留替代关系或归档记录。

### 2.5 文档与代码同步

改变架构边界、公开协议、数据模型、部署单元、安全语义或运维流程时，文档必须与代码在同一变更中更新。

## 3. 目录职责

```text
docs/
├── governance/    项目治理、文档制度和开发流程
├── architecture/  系统、代码、数据、部署和集成架构
├── standards/     编码、测试、API、安全和数据库规范
├── adr/           架构决策记录
├── plans/         可执行计划及归档
├── reviews/       代码、架构、发布和验收审查记录
├── runbooks/      可操作的部署、备份、恢复和故障手册
├── reference/     调研和外部参考，不直接构成项目规则
└── templates/     标准模板
```

### 3.1 根目录文档

仓库根目录只允许以下文档：

- `README.md`
- `AGENTS.md`
- `CONTRIBUTING.md`，需要时新增
- `SECURITY.md`，需要时新增
- 许可证文件

现有两份中文长文档属于迁移例外，已经在 `docs/README.md` 登记。新增长文档不得继续放置在根目录。

## 4. 文档类型

### 4.1 Baseline

定义当前必须遵守的长期规则，例如总体架构、代码架构和编码规范。

要求：

- 包含文档 ID、版本、状态和生效日期；
- 变更时说明兼容性和影响；
- 与其他 Baseline 冲突时必须通过 ADR 解决。

### 4.2 ADR

记录一个重要、长期、难以逆转或影响多个模块的架构决定。

需要 ADR 的典型场景：

- 新增部署单元或拆分微服务；
- 更换数据库、消息系统或对象存储；
- 改变领域边界或依赖方向；
- 引入新的认证、授权或租户模型；
- 改变事件一致性、幂等、重试和恢复语义；
- 引入影响全局的框架或 SDK。

不需要 ADR 的场景：

- 局部重构且不改变公开行为；
- 修复明确缺陷；
- 依赖补丁升级；
- 已有规范范围内的实现选择。

### 4.3 Plan

描述有起止条件的实施任务。

`docs/plans/current/` 只保存正在执行或下一步已批准的计划。完成、取消或被替代后移入 `docs/plans/archive/YYYY/`。

计划必须包含：

- 目标和非目标；
- 前置条件；
- 修改范围；
- 实施步骤；
- 测试和验收；
- 风险与回滚；
- 完成定义。

### 4.4 Review

记录审查事实、风险、结论和后续行动。Review 不是规范，但可触发规范、ADR 或计划变更。

### 4.5 Runbook

供开发或运维人员直接执行，必须包含前置条件、命令、验证、失败处理和回滚。

### 4.6 Reference

保存调研和外部参考。Reference 只能提供输入，不能覆盖 Baseline 或 ADR。

## 5. 文档状态生命周期

```text
Draft
→ Proposed
→ Baseline / Accepted
→ Superseded
→ Archived
```

- `Draft`：尚未准备评审。
- `Proposed`：内容完整，等待接受。
- `Baseline`：当前权威规则。
- `Accepted`：ADR 已接受。
- `Superseded`：有明确替代文档。
- `Archived`：不再参与当前决策。
- `Rejected`：ADR 被拒绝，但保留历史。

## 6. 命名规则

### 6.1 Baseline 和规范

使用稳定、不含版本号的英文大写文件名：

```text
CODE_ARCHITECTURE.md
RUST_CODING_STANDARD.md
API_DESIGN_STANDARD.md
```

版本写在文档头部，Git 保存历史。

### 6.2 ADR

```text
ADR-0001-modular-monolith-first.md
ADR-0002-object-storage-provider.md
```

编号一经使用不得复用。

### 6.3 Plan

```text
PLAN-0001-rust-service-foundation.md
PLAN-0002-document-processing-pipeline.md
```

### 6.4 Review

```text
2026-07-30-initial-implementation-review.md
2026-08-05-infra-01-acceptance-review.md
```

## 7. 文档头部元数据

Baseline、ADR 和 Plan 至少包含：

```text
文档 ID
版本
状态
日期
所有者或责任模块
替代/被替代关系，可选
关联 ADR/Plan/Issue，可选
```

不要在多个位置维护同一份版本清单。Git commit 是详细历史，文档头部只表达当前状态。

## 8. 权威关系

发生冲突时按以下顺序处理：

1. 已接受 ADR 对其决策范围内的旧 Baseline 具有覆盖力；
2. 最新 Baseline 优于旧 Baseline；
3. 架构和标准优于 Plan；
4. Plan 优于临时实现说明；
5. Review 只记录结论，不自动修改规范；
6. Reference 不具有约束力。

如果冲突无法按上述关系解决，必须停止扩大实现并新增 ADR。

## 9. 变更规则

### 9.1 必须同步文档的代码变更

- 新增、删除或重命名 crate；
- 新增、删除或重命名应用进程；
- 修改依赖方向；
- 修改公开 API、事件 Schema 或对象 key；
- 修改数据库迁移、事务或一致性规则；
- 修改认证、授权、租户或审计语义；
- 新增外部基础设施或 AI Provider；
- 修改部署、备份、恢复或故障处理方式。

### 9.2 文档评审检查

- 文档是否登记在 `docs/README.md`；
- 状态和权威关系是否明确；
- 是否与代码、配置和脚本一致；
- 是否包含验证和失败路径；
- 是否引用了已归档或失效内容；
- 是否重复定义其他文档已有规则。

## 10. 计划归档

计划满足以下任一条件时必须退出 `current`：

- 验收通过；
- 明确取消；
- 被新计划替代；
- 超过有效期且不再执行。

归档时更新状态，并记录：

- 最终提交或版本；
- 验收结果；
- 未完成项；
- 后续计划。

## 11. 自动化建议

后续 CI 应增加：

- 检查根目录是否新增未允许的 Markdown；
- 检查 `docs/README.md` 链接；
- 检查 ADR 编号重复；
- 检查 `plans/current` 中计划状态；
- 使用 Markdown lint；
- 检查文档中的相对链接。

## 12. 当前迁移安排

当前根目录的两份架构文档先保留原路径，避免初始提交后立即产生大规模移动。它们已由 `docs/README.md` 登记为权威基线。

后续迁移必须：

1. 在单独计划中移动到 `docs/architecture/` 和 `docs/runbooks/` 或 `docs/architecture/infrastructure/`；
2. 更新所有引用；
3. 在原位置保留短期跳转说明或一次性完成全仓更新；
4. 不保留两份可独立编辑的正文副本。

## 13. 验收标准

文档管理完成的最低标准：

- `README.md` 可定位项目、状态和权威文档；
- `docs/README.md` 是唯一文档入口；
- 架构、标准、ADR、计划、评审和 Runbook 有明确目录；
- 当前架构和编码规则已建立 Baseline；
- 初始实现审查已记录；
- 新增长期设计能够通过 ADR 和 Plan 进入实施；
- 编码 Agent 能通过 `AGENTS.md` 确定执行边界。
