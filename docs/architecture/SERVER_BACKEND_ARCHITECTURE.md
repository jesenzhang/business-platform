# 服务端后端架构基线

> 文档 ID：ARCH-BACKEND-001  
> 版本：1.0  
> 状态：Baseline  
> 生效日期：2026-07-30  
> 适用范围：整个 Rust 服务端 Workspace

## 1. 架构结论

服务端后端采用：

```text
战略 DDD
+ 模块化单体优先
+ 领域/应用/适配器分层
+ 依赖倒置与端口适配
```

这不是要求所有代码机械套用完整 DDD 战术模式，而是要求：

1. 业务能力按业务语义划分边界，而不是按数据库表、接口类型或技术组件划分；
2. 核心业务模型独立于交付协议、数据库、消息系统、对象存储和外部供应商；
3. 应用层通过用例组织业务，不让入口层和基础设施层承载业务决策；
4. 基础设施作为可替换适配器依赖核心，而不是核心依赖基础设施；
5. 复杂领域使用 Aggregate、Value Object、Domain Service 和 Domain Event，简单能力保持轻量；
6. 部署技术和产品选型通过适配器、配置和 ADR 落实，不进入核心业务规则。

## 2. 为什么采用 DDD

本项目不是单一 CRUD 服务，而是面向企业内部业务平台，包含：

- 用户、组织、客户、合同、项目、审批和财务；
- 文档、解析、字段建议和人工复核；
- 权限、多租户、审计和业务状态机；
- 长时任务、异步处理和跨系统协作；
- Web、开放 API、Worker 和 Agent 等多种入口。

这些能力的主要复杂度来自业务语义、规则变化、状态转换和跨模块协作，而不是 HTTP 或数据库访问。因此需要以领域模型和业务边界组织系统。

DDD 在本项目中的主要价值是：

- 建立稳定的业务边界；
- 统一业务语言；
- 防止数据库模型成为业务模型；
- 防止 Agent、UI、Worker 各自实现一套业务规则；
- 使基础设施替换不改变核心业务；
- 为未来按真实边界拆分服务提供基础。

## 3. DDD 的适用程度

### 3.1 战略 DDD：强制采用

所有业务模块都必须明确：

- Bounded Context；
- 业务职责和数据所有权；
- 对外公开的 Application API；
- 与其他上下文的关系；
- 统一语言；
- 同步调用和领域事件边界。

领域边界不能由以下因素直接决定：

- 一个数据库表；
- 一个前端页面；
- 一个 Controller；
- 一个消息 Topic；
- 一个基础设施产品；
- 一个 Agent Skill。

### 3.2 战术 DDD：按复杂度采用

以下场景应使用丰富领域模型：

- 存在多个业务不变量；
- 有明确生命周期或状态机；
- 多字段必须原子保持一致；
- 操作结果依赖当前业务状态；
- 规则会持续演进；
- 需要产生领域事件。

以下场景可以保持轻量：

- 简单只读查询；
- 无业务不变量的配置数据；
- 明确的字典和参考数据；
- 单纯协议适配；
- 基础设施健康检查。

禁止为了形式完整而为所有表创建空洞的 Aggregate、Repository 和 Domain Service。

## 4. 顶层架构

```text
Delivery / Entry
Web API / OpenAPI / Worker / Scheduler / Agent Adapter
                         │
                         ▼
Application
Use Case / Command / Query / Process Coordination
                         │
                         ▼
Domain
Bounded Context / Aggregate / Entity / Value Object / Policy
                         ▲
                         │ Ports
                         │
Infrastructure Adapters
Persistence / Messaging / Storage / External Providers
                         ▲
                         │
Composition Root
配置、实例化、依赖注入、进程生命周期
```

权威依赖方向：

```text
外层依赖内层
实现依赖抽象
核心不依赖交付和基础设施
```

## 5. 分层职责

### 5.1 Domain

Domain 表达业务事实和业务规则，包含：

- Aggregate、Entity、Value Object；
- 领域策略和领域服务；
- 领域状态转换；
- 领域错误；
- 领域事件；
- 业务不变量。

Domain 不负责：

- HTTP、JSON 协议和状态码；
- 数据库查询和行映射；
- 消息发布实现；
- 文件存储实现；
- 外部供应商请求；
- 进程启动和配置加载。

领域模型必须可在无数据库、无网络、无外部服务的环境中测试。

### 5.2 Application

Application 表达系统用例，负责：

- 接收业务意图；
- 校验调用上下文；
- 协调领域对象；
- 调用所需端口；
- 定义事务和幂等边界；
- 协调审计和事件；
- 返回协议无关的结果。

Application 不负责：

- 解析 HTTP Header 或 Cookie；
- 编写 SQL；
- 拼接供应商请求；
- 选择具体基础设施产品；
- 返回框架专用 Response；
- 保存全局基础设施客户端。

### 5.3 Delivery / Entry

入口层包括：

- Web API；
- OpenAPI；
- Worker 消费入口；
- Scheduler；
- Agent Adapter；
- 管理命令和 CLI。

入口层只负责：

```text
协议输入
→ 身份和上下文提取
→ 构造应用命令
→ 调用用例
→ 协议输出
```

入口层不得实现业务状态机、业务权限规则或直接访问数据存储。

### 5.4 Infrastructure

Infrastructure 提供技术实现，例如：

- 持久化适配器；
- 消息适配器；
- 对象与产物存储适配器；
- 外部 AI/OCR/文档服务适配器；
- 身份供应商适配器；
- 时钟、ID 和遥测适配器。

基础设施类型和错误不得向上泄漏。核心层只看到稳定的业务或能力接口。

### 5.5 Composition Root

`apps/*` 是组合根，负责：

- 加载和校验配置；
- 创建具体适配器；
- 将实现注入 Application；
- 启动 API 或 Worker；
- 管理生命周期和优雅关闭；
- 初始化可观测性。

只有组合根可以知道完整的技术装配关系。

## 6. 端口所有权原则

端口由需要该能力的内层定义，而不是由外部产品定义。

例如核心需要的是：

```text
保存和读取业务聚合
持久化并恢复任务
保存和读取大型产物
调用文档识别能力
发布业务通知
获取时间
```

核心不应该定义成：

```text
执行某种 SQL
发送某个 Broker Topic
写入某个 Bucket
调用某厂商 HTTP Endpoint
```

端口名称、输入和输出必须表达业务或通用能力语义，不表达适配器实现细节。

## 7. 业务领域与通用能力的关系

系统分为：

### 7.1 核心业务上下文

例如：

- Contract；
- Approval；
- Customer；
- Project；
- Finance；
- Document。

它们表达企业业务事实、规则和状态。

### 7.2 支撑业务上下文

例如：

- Identity；
- Organization；
- Notification；
- Audit；
- Policy。

它们支撑核心业务，但仍有明确业务语义和边界。

### 7.3 通用平台能力

例如：

- Workflow / Durable Job；
- Object and Artifact Storage；
- Messaging；
- Observability；
- AI Provider Integration。

通用平台能力可以拥有自己的领域模型，例如任务、步骤、重试、取消和租约，但不得反向侵入具体业务领域。

## 8. 长时任务的边界

长时任务必须区分两类状态：

### 8.1 业务过程状态

由业务上下文拥有，例如：

```text
文档已提交解析
解析结果待复核
字段建议已应用
```

这些状态影响业务意义，属于 Document 或其他业务上下文。

### 8.2 执行机制状态

由通用任务能力拥有，例如：

```text
任务待执行
步骤执行中
等待重试
请求取消
执行失败
```

这些状态描述可靠执行，不应成为具体业务模型的基础设施细节。

业务上下文通过应用级能力请求任务执行并接收业务结果；通用任务系统负责持久化、调度、恢复和执行语义。两者通过稳定接口和事件协作。

## 9. 数据与事务边界

- 每个 Bounded Context 拥有自己的数据模型和写入规则；
- 其他上下文不得直接更新其私有表；
- 事务边界由 Application 用例根据业务原子性定义；
- Domain 不接触数据库事务对象；
- 单一上下文内优先使用本地事务；
- 跨上下文流程使用领域事件、幂等、状态机和补偿；
- 不伪装成跨系统强事务；
- 基础设施负责实现事务、锁、并发控制和可靠发布，但不能改变业务语义。

## 10. 上下文间协作

优先顺序：

1. 对方公开的 Application API；
2. 明确的上下文端口；
3. 领域事件；
4. Anti-Corruption Layer，用于隔离外部或遗留模型。

禁止：

- 跨上下文直接写表；
- 共享可变领域实体；
- 将一个上下文的数据库结构作为另一个上下文的公开协议；
- 为减少一次调用而破坏数据所有权。

## 11. 模块化单体与微服务

当前采用模块化单体：

- Bounded Context 首先表现为代码和数据所有权边界；
- crate 不自动等于独立服务；
- 同一部署进程内仍需遵守上下文边界；
- 不因使用消息或 Worker 就自动定义为微服务。

只有在独立扩缩容、安全隔离、故障隔离、发布周期、数据所有权或运行资源形成客观需求后，才通过 ADR 拆分部署单元。

## 12. 基础设施独立性

总体架构基线只规定能力语义和非功能要求，不将具体技术产品写入核心规则。

具体技术的角色应记录在：

- Infrastructure Adapter；
- Composition Root；
- 部署配置；
- ADR；
- Runbook；
- 契约测试。

例如，核心架构规定“需要可靠任务状态存储、执行通知和产物存储”；至于当前适配器采用何种数据库、消息系统和对象存储，由实现配置和 ADR 决定。

替换基础设施时，允许修改：

- 适配器；
- 配置；
- 部署；
- 运维手册；
- 契约测试。

不应修改：

- 业务不变量；
- 业务用例；
- 领域状态；
- 公开业务语义。

## 13. AI 与 Agent 边界

- AI 输出是候选结果，不是业务事实；
- AI Provider 属于外部能力适配；
- 业务上下文负责结果校验、冲突判断和正式应用；
- Agent 是入口适配器，不拥有业务规则；
- Web、Worker、Agent 和其他入口复用同一 Application 用例；
- Agent 和 AI 的可替换性不得改变业务核心。

## 14. 架构适配测试

必须通过自动化规则持续验证：

- Domain 不依赖交付框架和基础设施 SDK；
- Application 不依赖具体适配器；
- 入口层不直接访问数据库；
- Infrastructure 类型不进入公开核心接口；
- 跨上下文不得直接依赖对方 Infrastructure；
- 核心用例可通过 Fake/In-Memory 端口测试；
- 适配器通过真实依赖契约测试验证。

未来应将依赖规则转化为 CI 中的架构适配测试或 Workspace 依赖检查。

## 15. 实施准则

实现新能力时依次回答：

1. 它属于哪个 Bounded Context？
2. 它是业务规则、应用用例、入口协议还是基础设施实现？
3. 业务不变量是什么？
4. 数据所有者是谁？
5. 哪些能力需要通过端口获得？
6. 事务和幂等边界是什么？
7. 是否需要领域事件或补偿？
8. 是否引入了不必要的战术 DDD 复杂度？
9. 是否有基础设施类型向核心泄漏？
10. 是否需要 ADR？

## 16. 最终原则

> 业务复杂度由领域模型承载，流程协调由应用用例承载，技术复杂度由适配器承载，运行装配由组合根承载。

> 核心系统描述“系统必须做什么”，基础设施描述“当前如何实现”。

> 任何基础设施替换都不应迫使业务核心重写。
