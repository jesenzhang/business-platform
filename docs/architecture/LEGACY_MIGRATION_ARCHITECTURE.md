# 遗留系统迁移架构

> 文档 ID：ARCH-MIGRATION-001  
> 版本：1.0  
> 状态：Baseline  
> 生效日期：2026-07-30  
> 适用范围：现有 Python 后端、历史数据、第三方接口和新 Rust 平台之间的渐进迁移

## 1. 目标

迁移目标不是一次性重写，而是在业务持续运行的前提下：

- 逐步建立 Rust 平台权威能力；
- 保持数据完整和接口连续；
- 避免双写失控；
- 可逐步回退；
- 让新旧系统边界清晰；
- 最终关闭遗留实现而不是永久并存。

## 2. 原则

1. 先确定业务和数据所有权，再迁移代码；
2. 使用 Strangler Fig 渐进替换；
3. 遗留模型通过 Anti-Corruption Layer 隔离；
4. 单一数据在任一阶段只有一个权威写入者；
5. 双读可以短期存在，双写必须受控且可校验；
6. 所有迁移阶段都有进入、退出和回滚条件；
7. 历史数据迁移与在线行为迁移分开设计；
8. 不因兼容遗留系统污染新 Domain Model。

## 3. 迁移单元

迁移以业务能力或 Bounded Context 的垂直切片为单位，不以数据库表或 Controller 数量为单位。

每个迁移单元至少包括：

- 业务用例；
- 数据所有者；
- API/事件；
- 历史数据；
- 权限和审计；
- 后台任务；
- 监控和回滚。

## 4. 典型阶段

### Phase A：Observe

- 建立现状清单；
- 捕获 API、数据、规则、任务和运行指标；
- 明确隐含业务规则；
- 建立契约测试和 Golden Dataset。

### Phase B：Encapsulate

- 在新平台建立 Anti-Corruption Layer；
- 遗留接口转换为内部稳定模型；
- 不直接复用遗留 DTO 和数据库 Row。

### Phase C：Shadow Read/Compute

- 新实现并行计算或读取；
- 不影响正式结果；
- 对比差异和性能；
- 记录不一致原因。

### Phase D：Controlled Cutover

- 按租户、用户、业务类型或百分比切流；
- 新系统成为该范围内唯一写入者；
- 保留受控回退窗口。

### Phase E：Migrate History

- 批量迁移历史数据；
- 校验数量、checksum、业务不变量和引用；
- 保存迁移批次和错误记录。

### Phase F：Retire

- 停止遗留写入；
- 关闭读取和任务；
- 清理凭证、路由和运维依赖；
- 归档数据和文档；
- 明确完成证据。

## 5. 权威写入者

每个迁移阶段必须在表格中明确：

| 能力/数据 | 遗留系统 | Rust 平台 | 权威写入者 | 同步方向 |
|---|---|---|---|---|
| 示例 | Read/Write | Shadow Read | Legacy | Legacy → Rust |

禁止同时允许新旧系统对同一权威字段无协调写入。

## 6. 双写

优先避免应用层双写。

可选策略按优先顺序：

1. 唯一写入者 + 事件同步；
2. 数据变更捕获或 Outbox；
3. 迁移网关协调写入；
4. 短期受控双写，带幂等、对账和退出期限。

双写必须定义：

- 成功顺序；
- 部分失败；
- 重试；
- 幂等；
- 对账；
- 冲突解决；
- 结束日期。

## 7. 数据迁移

### Extract

- 固定源快照或增量游标；
- 记录批次和水位；
- 不信任遗留数据天然符合新模型。

### Transform

- 通过 ACL/Translator 映射；
- 明确默认值、枚举转换、时区和精度；
- 无法映射的数据进入异常队列。

### Load

- 使用幂等 Upsert 或导入键；
- 维护源 ID 与新 ID 映射；
- 不绕过新系统业务不变量，必要时使用受控迁移用例。

### Verify

- 数量；
- checksum；
- 关键字段；
- 引用完整性；
- 业务不变量；
- 随机抽样；
- 用户验收。

## 8. 接口迁移

- Gateway 根据路由规则转发到新旧实现；
- 新平台公开稳定 API；
- 遗留差异在 ACL 内处理；
- 切流规则可观测和可回滚；
- 不让客户端长期感知两套业务语义；
- 破坏性变化使用版本和兼容窗口。

## 9. 事件迁移

- 定义新旧事件映射；
- 避免同一事实由两边重复发布；
- 使用 event_id 和 source 标记；
- 消费者幂等；
- 切换发布者时明确水位；
- 历史重放与实时事件分离；
- 不把遗留技术消息直接作为新领域事件。

## 10. 后台任务迁移

- 盘点 Cron、队列、人工脚本和数据库任务；
- 明确任务所有者、输入、输出和幂等；
- 在切换前停止旧调度或建立唯一 leader；
- 迁移未完成任务和重试状态；
- 防止新旧 Worker 同时执行同一业务副作用；
- 对账任务结果。

## 11. 文件迁移

- 保存源路径、目标 ArtifactRef、checksum、大小和状态；
- 支持断点续传和重试；
- 校验对象数量和 checksum；
- 权限和租户关系重新验证；
- 失败对象进入可恢复清单；
- 不直接把遗留绝对路径暴露到新业务模型。

## 12. 身份与权限迁移

- 用户映射与组织映射分离；
- 角色名称不能直接假设语义一致；
- 权限转换需业务确认；
- 切换时保持最小权限；
- 未映射主体默认拒绝；
- 迁移和委托操作完整审计。

## 13. Shadow 验证

Shadow 模式比较：

- 响应和业务结果；
- 错误码；
- 性能；
- 事件；
- 任务输出；
- 权限决策。

差异必须分类：

- 遗留缺陷；
- 新实现缺陷；
- 业务规则不明确；
- 数据质量问题；
- 允许差异。

## 14. 切流

支持按：

- 内部测试用户；
- 租户；
- 组织；
- 业务类型；
- 资源 ID；
- 百分比。

切流控制必须：

- 服务端管理；
- 可审计；
- 有生效时间；
- 有回滚；
- 不允许客户端任意选择绕过。

## 15. 回滚

回滚前必须定义：

- 新系统已产生数据如何处理；
- 是否需要反向同步；
- 哪些操作不可逆；
- 消息和任务水位；
- 文件和外部副作用；
- 回滚验证。

当新系统已成为权威写入者后，不能仅通过改路由无条件回滚。

## 16. 可观测性

迁移 Dashboard 至少包含：

- 新旧流量比例；
- 成功率和延迟；
- Shadow 差异；
- 同步积压；
- 数据迁移进度；
- 对账异常；
- 回滚次数；
- 遗留调用剩余量。

## 17. 安全

- 迁移凭证最小权限和限时；
- 迁移数据加密；
- 临时文件和导出按时清理；
- 生产数据不得复制到非受控环境；
- 错误报告脱敏；
- 迁移操作审计；
- 完成后撤销旧凭证和网络访问。

## 18. 每个迁移切片完成定义

- [ ] 新业务边界和数据所有权明确；
- [ ] ACL 和契约测试完成；
- [ ] 历史数据迁移和对账通过；
- [ ] 新系统成为唯一权威写入者；
- [ ] 后台任务和事件无重复；
- [ ] 监控和回滚演练通过；
- [ ] 遗留入口、凭证和运维依赖关闭；
- [ ] 文档和 ADR 更新；
- [ ] 明确最终提交和关闭日期。

## 19. 推荐迁移顺序

优先：

1. 基础调用上下文和只读查询；
2. Document Metadata 等低风险垂直切片；
3. 文档处理和后台任务；
4. Customer；
5. Contract 的低风险用例；
6. Approval 和正式写状态；
7. Finance 等高风险能力。

最终顺序以业务依赖和风险评估为准。
